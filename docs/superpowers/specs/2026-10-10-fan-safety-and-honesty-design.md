### W1 的复核（本轮新增，2026-10-11）

W1 声称的机理是"`guard()` 位于被 `except Exception: pass` 覆盖的 try 内部，
任何持续性异常会让循环永远不再调用它"。**这条机理不成立**，原描述已在下面保留以便追溯。

采集循环的真实次序是 `apply_persisted_state()` → `guard()` → `snapshot()` → DB 写入。
看门狗排在 `snapshot()` 与数据库写入**之前**，所以后两者的持续性异常只可能让
这一轮的后半段被跳过，**下一轮开头仍然先调 `guard()`** —— 被跳过的从来不是看门狗本身。
唯一能挡在 `guard()` 前面的是 `apply_persisted_state()`，而它在 `try` 之前就置了
`_APPLIED = True`，且 `get_state()` 自带 `except Exception`；即使它抛了，
下一轮也是同样的次序，循环不会停在异常点。

所以 W1 作为"可达的停转/欠冷却路径"不成立：看门狗的执行频率没有被削弱。
**本分支不声称关闭它**，触发表与目标行也据此改成"三条"。
若日后要动采集循环，真正的加固对象是"`guard()` 独立于采集周期"（例如按温度时钟
单独调度），那是另一个改动，不在本轮范围。

另有两条我自己的声称被证伪：

| | 声称 | 实测 |
|---|---|---|
| **L1** | `319fdc3`："Mutations that survive: none" | 我把下界检查改成 `[ "$E" -lt 0 ]`（等于关掉），`test_control_paths` 仍报 `fails=0` |
| **L2** | `b06a191`："last-requested-size 护栏让反馈回环 fail closed" | 该护栏比较 `last.w`/`last.h`，而 `sizeOf` 返回 `{width,height}` —— 永远不相等，**从不触发** |

以及三处文档与实现不符：`SECURITY.md` 的 token 声称、`9eb0043` 的"单一事实源"（实为两个文件）、
sanitiser 声称 5 类规则而实际编译 3 条且 `--list` 与实现不符。

## 设计

### 第一部分：风扇安全（Stage 1）

三处修改，共约 10 行。**同批落地**的理由：它们是同一族（"被命令停转 / 降级 / 谎报成功"），
且 F2 与 W2 会互相放大——恢复一个安全档位正是让 W2 残余窗口可生存的前提。

**S1. `pfanel.py:413` —— level 0 必须恢复为安全下限**

```python
# set_level 把档位钳在 >=1，所以 0 从来不是一次"有意的选择"，
# 它是"从没按过档位按钮"的默认状态（:79）。把它当成"无可恢复"，
# 会让 free 曲线在每次 pfanel 启动（含每次 deploy）后把风扇留在 0。
if st.get("level"):
    acpi(FSL, "1 %d" % int(st["level"]))
```

改为：把 `0` 与 `None` 同等对待，回落到 `_FSL 1 25`（`_FPS` 表最低档），并记日志说明是回落而非恢复。
`set_level` 的钳位保证真实档位永不为 0，所以这条只影响"默认值"这一种情形。

**S2. `core/pfand:193` —— 自检补 `E >= CAP`**

在既有的三条关系里加一条：`[ "$E" -lt "$CAP" ]`。理由写在注释里：应急档低于上限意味着
在最危险的温度下散热比日常还弱，而日志仍会写"满速"——这既是欠冷却也是谎报。

**为什么不全盘改用 `validate_params`**：守护是 bash，`validate_params` 是 Python，
每次启动 fork 一个解释器的代价与失败面都更大。本轮只补这条**有硬件后果**的关系，
其余（L0..L4 ≤ CAP、IV ≥ 2、DWELL ≥ IV、TRIM/GAIN 范围）记录为待办，不在本轮。

**S3. `set_curve` —— 检查 `systemctl` 结果，失败则回滚**

写档位后验证守护真的起来了；失败时切回 `cool`（`set_curve("auto")` 已有这个兜底路径），
并且**不持久化**该状态（否则每次重启重放同一个坏状态）。

**成功判据必须同时包含两件事**，这是自审时发现的一处真实歧义：
守护 `is-active` **且** 设备上读回一个非零档位。

只查 `is-active` 是不够的：守护可能活着却正卡在 `ensure_s0i3()` 的握手窗口里
（该窗口内 `_FSL` 为 0，正是本项目反复踩到的那个窗口）。那种情况下 `is-active` 返回
active，但设备上没有档位 —— 判成成功就等于没做检查。

**为什么不能用"立即 `is-active`"**：守护重启期间会短暂返回非 active，立刻检查会产生
假回滚。所以是**有界重试**（约 5 × 1s），每次同时满足上面两个条件才算通过。

### 第二部分：停止宣称假话（Stage 2）

**S4. 给 `test_control_paths` T12 补行为测试**

现状是 grep 源码里的字符串。改为：把 `config/pfand.conf.example` 复制成一份 `E=0` 的变体，
用 `fake/` 跑**真实的 `core/pfand`**，断言设备收到的是 `_FSL 1 100` 而不是 `_FSL 1 0`，
且日志含"档位下界非法"。

`fake/` 已经支持这个形状（`test_pfand_loop` T3 就是这么做的），约 5 秒。
这是本轮唯一一处**新增测试**，因为它是唯一一处"声称有变异验证而实际没有"的安全守卫。

**S5. 死护栏 `b06a191` —— 修好而不是删掉**

`app.js` 的比较改成 `last.width`/`last.height`。保留它的理由：主修复（`sizeOf` 量父容器）
是对的，但反馈回环护栏是第二道防线，而项目刚刚两次因为"声称存在实际不存在的防线"受损。
同时 `test_panel_split` T4 从 grep `parentElement` 改为**限定在 `sizeOf` 函数体内**查找
（现状下该字符串出现两次，改 `sizeOf` 留 `fitChart` 仍会绿）。

**S6. `PANEL_DIR` —— 让声称成立，而不是改声称**

分歧的根源：deploy/smoke 读仓库的 `platform.conf.example`，pfanel 读机器上的
`/etc/pfan/platform.conf`，而那台机器上的文件**没有 `PANEL_DIR` 这一行**（是 `pfan detect` 生成的）。

修法：`pfan detect --write` 也输出 `PANEL_DIR`；`deploy.sh` 在 `/etc/pfan/platform.conf`
已存在但缺该键时补上（幂等）。这样"改一处"才真的成立。

**不**改默认值到 `/usr/local/share/pfan` —— 那是一次独立的迁移，不属于本轮。

**S7. sanitiser —— 规则与 `--list` 一致**

补两条缺失规则（`user@host` SSH 目标、私网网段），但**先定策略**：`scripts/sanitize.allow`
是 gitignored 的，意味着 fork 永远无法让这个门变绿——那它对 fork 就是装饰。

策略决定：**`--list` 输出实际编译的规则，而不是散文**；`sanitize.sh` 自身的规则文本行
从扫描中排除（否则它过不了自己的门）；`ci.sh`/`hooks/pre-push`/ledger 里三处"19"改成不写死数字
（从脚本输出取）。

**为什么不是"补规则然后挨个豁免"**：上一次那个门"静默杀掉每次推送"就是这么来的。
先把"门能变绿"这件事解决，再谈它拦什么。

### 第三部分：安全文档（Stage 3，仅文档）

按你的决定，**不改鉴权代码、不改网络暴露**，只把 `SECURITY.md` 的假声明改成事实。

必须改的（每条都经专家核对过代码）：

| 位置 | 现在的声称 | 实际 |
|---|---|---|
| `SECURITY.md:16` | 写接口是 `POST /api/level`、`/api/curve` | 没有这些路由。`do_POST` 从不读 `self.path`，写操作由 **JSON body 的键**决定，任意路径皆可 |
| `:16-19` | 写接口靠 `X-Pfan-Token` 无条件保护 | 代码层面为真，但 token 由 `/pfan.js` 公开下发 → 对**非浏览器客户端等同无鉴权** |

| `:22` | 免鉴权读接口是三个 | 不完整：还有 `/api/history`、`/api/params`（返回 `/etc/pfand.conf` 的绝对路径）、`/api/profile`（泄漏 `guard_temp`）、`/api/mode`、`/api/levels` |

同时文档必须说清**仍然有效**的边界，否则会矫枉过正：Origin 白名单是真实有效的浏览器 CSRF 边界
（专家确认无法被别的源绕过）；无 ACAO 阻止跨源读遥测；ufw 使 8789 仅 LAN；
`guard()` 的 82°C 上限是写路径危害的实际天花板（`{"profile":"free"}` + `{"level":1}`
的最坏可达状态约 82°C）。

**以及一句话说明真实模型**：隧道的可达性就是边界；应用层不认证任何人；兜底的是 guard。

## 被否决的方案

**`pfand` 的 `trap`（F1）—— 否决，本轮不做。**
两个独立理由。其一，它**可能让情况变糟**：`pfand:176` 在曲线非 s0i3 时 `exit 0` **正常退出**，
发生在 `ensure_s0i3` 之前；天真的 `trap 'setL 25' EXIT` 会在每次切曲线时踩掉用户故意设的
quiet/cool 固件曲线。其二，它**最不紧急**：`Restart=on-failure, RestartSec=15` 意味着窗口内
单次崩溃约 15 秒自愈；只有模块同时掉线才不可恢复，而那时 `pfanctl.service` 会挡住重启。
专家建议等 Stage 2 的变异测试落地后再做——先有能抓住踩踏回归的测试。

**鉴权代码 / 网络暴露 —— 否决（你的决定）。**
文档改完后，本轮不动 `pfanel.py` 的 token 注入、不动隧道。专家记录了备选路径及其前置
（CF Access 能否建成功，AGENTS.md 记为未开通），留给后续单独决策。

**`PANEL_DIR` 默认值迁移 —— 否决。** 一次独立的迁移，会改目标机上的实际写入位置。
本轮只让"改一处"这个声称成立。

**Stage 4 安装/卸载流程 —— 否决。** 约一天工作量，且会把当前仍在运转的行为固化进文档。

## 风险与不做会怎样

- **S1/S2 触及正在运行的守护与后端**：需要一次部署。恢复点机制已验证为 10/10 完整。
- **S2 只补一条关系而非全盘对齐**：记录在案。`validate_params` 拒绝而守护接受的其他组合
  （L0..L4 > CAP 等）仍存在，但它们不产生"最热时比日常更弱"这个后果。
- **不做 trap**：窗口内崩溃约 15 秒无档位。可接受，且做错的代价高于不做。
- **不改鉴权**：写路径对能访问面板的人保持敞开。文档会如实写明这一点——这至少意味着
  下一个人不会因为相信文档而做出更糟的决定。
